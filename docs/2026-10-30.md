# SokoBot optimization and refactoring audit log

This document records diagnostic sessions, profiling results, bug findings, and refactoring steps. The sessions covered the **SokoBot** C++20 solver and its telemetry pipeline.

Note: Later refactoring renamed several identifiers in this log. The names below match the code on the day of each entry. See `architecture.md` for the current module layout.

---

## 1. Executive summary and milestones

* **Phase 1 (switch penalty diagnostics):** The team analyzed why `switch_penalty` cut the search by 83%. They found goal-overshoot and entrance-clogging effects. Goal arrivals interact with switch costs.
* **Phase 2 (thread portfolio disparity):** The team explained why Thread 0 won almost every puzzle. Two causes appeared. Thread 0 started first and used cheap $O(1)$ Manhattan calculations, while other threads used array lookups. A bug also overwrote the Hungarian matching on 7 of 8 nodes.
* **Phase 3 (Google C++ Style modularization):** The team split the monolithic `solver.cpp` into single-responsibility translation units. The units were `board.cpp`, `heuristic.cpp`, `deadlock.cpp`, `solver.cpp`, `bench.cpp`, and internal headers. All units live in the namespace `soko::`.
* **Phase 4 (deadlock engine breakthroughs):**
  * The team found that `FindPiCorral()` stopped after the *first* corral. It never checked the other deadlocked corrals.
  * The team caught goal-room clogging with `HasDeadEmptyGoal` and `goal_depth_` funneling.
* **Phase 5 (stagnation and deep-pocket escapes):** Complex maps (`1-5`, `1-9`, `1-40`) trapped the search in local minima. The minima locked the priority queue for millions of iterations. The team added heap perturbations that stagnation triggers.
* **Phase 6 (thread portfolio differentiation):** The team replaced the global engine flags with per-thread feature toggles (`ThreadConfig`). Four distinct engines now race at the same time. The engines no longer flip-flop between regressions.

## 2. Chronological audit and root-cause analysis

### Audit item #1: `switch_penalty` mechanics and the goal-overshoot anomaly
* **Symptom:** The solver charged $+2.5\text{M}$ when a box landed on a goal and the next push moved a different box. Pushing the finished box *off* the goal cost only $+1.0\text{M}$ in heuristic loss. The solver therefore preferred to push a finished box *past* its goal.
* **Experiment:** The team tested `if (switched_box && !is_goal_[curr.last_dest]) ++next.switches;`. This made switching off a goal free.
* **Finding:** The change sped up maps like `C-10` by $2\times$ down to $h=2$. It broke maps with narrow goal-room entrances (`original2`). When switching off a goal is free, the bot stops at the *entrance* goal tile. It does not pack the goal room from back to front. The packed entrance then blocks later boxes.
* **Resolution:** The team kept the baseline switch penalty for classic layouts. They added the **goal-room funnel (`goal_depth_`)**. The funnel uses the heuristic gradient to favor back-to-front packing. It does not rely on arbitrary switch penalties.

---

### Audit item #2: Thread 2 Hungarian heuristic bug
* **Symptom:** In `flags.h`, Thread 2 had `.hungarian = true`. Benchmark profiling still showed heuristic times and node choices close to greedy matching.
* **Root cause:** The function `Solver::CalcHeuristicIncremental` held this code:
  ```cpp
  constexpr u16 kRefreshInterval = 8;
  if (cfg_.heuristic == Heuristic::kNone || depth % kRefreshInterval == 0) {
    return CalcHeuristic(boxes, goal_of);
  }
  // Greedy 1-box update executed here on depths 1..7
  ```
  The function `CalcHeuristic` runs the Hungarian matching. The code called it once every 8 depth increments. On the other 7 steps, `CalcHeuristicIncremental` matched the moved box greedily. It overwrote the global matching array `goal_of`. Thread 2 ran greedy matching $87.5\%$ of the time.
* **Resolution:** The team changed the condition to `cfg_.hungarian || depth % kRefreshInterval == 0`. They later throttled it to `depth % 4 == 0` or goal events. This kept the nodes per second high.

---

### Audit item #3: Telemetry and benchmark thread visibility
* **Symptom:** `bench.cpp` recorded only total moves, nodes, and elapsed times. The telemetry did not show which thread won. It also did not show whether Thread 0 won by algorithm or by spawn-order latency on trivial maps under $5\text{ms}$.
* **Resolution:**
  1. The team added `std::atomic<int> g_winning_thread` to `solver.h`. `ExpandNode` stores the winning thread ID when it finds a solution.
  2. The team changed `native/src/tools/bench.cpp` to show a `thread` column (`T0` to `T3`). It also writes thread IDs to the benchmark CSV files. It counts wins separately for **all maps** and for **hard maps ($\ge 50\text{ms}$)**.

---

### Audit item #4: Refactoring to Google C++ Style
* **Symptom:** All procedural solver code sat in one `solver.cpp` file of about 1,200 lines. Isolated tests and heuristic experiments were brittle.
* **Resolution:** The team split `native/` into headers and compilation units that follow the Google C++ Style Guide:
  * `include/solver_internal.h` held the internal types (`SokoState`, `PQNode`), the memory allocators, the bitwise cut-vertex tables, and the class declaration.
  * `src/board.cpp` held the static parsing, the Zobrist initialization, the reverse BFS pull-distance computation, the tunnel macros, and the path reconstruction.
  * `src/heuristic.cpp` held the Hungarian $O(B^3)$ matching, the greedy nearest-goal matching, the LIS-based linear conflict penalties, and the incremental 2-opt swaps.
  * `src/deadlock.cpp` held the 2x2 corner deadlock filters and the static and dynamic freeze detection (`FrzFrozen`). It also held the PI-corral identification and the bipartite feasibility check (Hall's marriage theorem).
  * `src/solver.cpp` held the 4-ary min-heap priority queue and the 32-bit packed transposition table (`HashInsert`). It also held the node expansion and the worker thread lifecycle.
  * The team placed all internal routines in `namespace soko`. The C ABI function `SolveSokoban` stayed compatible.

### Audit item #5: PI-corral abort bug and corral over-pruning
* **Symptom:** On map `1-5_Sokoban-Original-and-Extra-5`, the search expanded $8,759,668$ nodes in $36.5\text{s}$. It exhausted the 10-million-state pool and failed. It recorded only $6,057$ corral deadlocks.
* **Root cause:** The function `FindPiCorral()` held this code:
  ```cpp
  if (is_pi) {
    if (!any_valid_inward) {
      result.is_deadlock = true;
      return result;
    }
    result.corral_id = cid;
    return result; // <--- Aborts scan on the very first corral found!
  }
  ```
  Some maps have several closed areas. One example has a goal room on the left and a closed box cluster at the bottom right. The scan stopped after the first corral. Corral 1 could have legal inward pushes while Corral 2 was deadlocked. The solver never detected that deadlock.
* **Resolution:**
  1. The team changed `FindPiCorral()` to scan all corrals on the board.
  2. The team checked inward pushes against static dead squares (`min_dist_[to] >= kUnreach`).
  3. On `1-5`, the solver caught **$1,009,272$ deadlocked corrals**. That is a $166\times$ increase. An unsolvable timeout became a **$1.63\text{s}$ solve**.

---

### Audit item #6: Stagnation escape heap corruption on large maps (`1-40`)
* **Symptom:** Map `1-40` is $17 \times 16$ and starts at $h=425$. The solver fell quickly to $h=203$. It then stalled for $5\text{M}$ expansions and ran $53.9\text{s}$ without a result. Profiling showed $23.1\text{s}$ in `kPlayerFlood`. It also showed a $300,000$-state BFS bulge at depth 35.
* **Root cause:**
  1. The original stagnation escape added `g * 1.5M` to *every* node in `pq_`. It did this every $25,000$ stagnant pops.
  2. On a large map, `pq_size_` passed $4,000,000$ entries. Re-heapifying the whole queue cost too much time.
  3. After 40 triggers, the depth penalties reached $+60\text{M} \times g$. Deeper nodes ($g > 150$) could never pop. The queue turned into a flat breadth-first search at depth 35.
* **Resolution:**
  1. **Pocket sinking:** The team limited stagnation penalties to the top $16,384$ nodes in `pq_`. These nodes are the stalled pocket. Other branches deeper in the queue no longer collected runaway penalties.
  2. **Sawtooth penalty release:** The team removed the accumulated depth brake at intervals. New branches could then run deep, greedy dives without inhibition.
  3. **Corral-only flood fill:** A box push can open a corral. The solver then flooded only the newly connected corral cells (`reach_ != reach_seq_`). It no longer ran a full board BFS. This sped up `kPlayerFlood`.

---

### Audit item #7: The goal-freeze false deadlock (`1-7` versus `1-9`)
* **Symptom:** The team added `HasDeadEmptyGoal` and a strict freeze check. Map `1-9` then solved in $1.40\text{s}$. Map `1-7` was declared unsolvable.
* **Root cause:**
  1. `FrzFrozen` sets `frz_mark_[pos] = frz_seq_` to detect recursive cycles. Sometimes the recursive check found that a box was *not* frozen. The mark stayed set. Later checks in the same expansion then treated a movable box as frozen.
  2. `FindPiCorral()` checked whether a box outside the corral was blocked dynamically (`Check2x2`). The check ignored that the player could move that outer box away later. The code marked such inward pushes as dead. Legitimate corrals then looked deadlocked.
* **Resolution:** The team cleared `frz_mark_[pos] = 0` whenever `FrzFrozen` returned `false`. They limited the corral inward-push filter to immutable static dead squares (`min_dist_[to] >= kUnreach`).

---

### Audit item #8: Move to a fully parameterized portfolio
* **Symptom:** Maps `1-5`, `1-6`, `1-7`, and `1-9` had conflicting structural needs:
  * `1-5` and `1-9` needed `goal_room_funnel`, `HasDeadEmptyGoal`, and aggressive multi-corral pruning.
  * `1-6` needed a lower switch penalty ($1.5\text{M}$) and player-walk tie-breaking ($10\text{K}$).
  * `1-7` and `original2` needed the classic baseline. That baseline has no goal-room funnel and no goal-freeze check.
  * `C-10` and `1-40` needed zero-switch interleaving or pocket-sink deep diving.
* **Resolution:** The team made these features first-class fields in `ThreadConfig`:
  * `bool goal_room_funnel`
  * `bool goal_freeze_check`
  * `bool aggressive_corral`
  * `StagnationMode stagnation_mode`

  Each thread received a distinct engine profile. All four map types now solve in parallel competition without regressions.

## 5. Summary of modified files

1. **`native/include/flags.h`**: It holds the thread portfolio definitions with independent engine feature flags.
2. **`native/include/solver.h`**: It holds Google-style header guards, trace event definitions, and the thread victory atomics.
3. **`native/include/solver_internal.h`**: It held the internal structures (`SokoState`, `PQNode`), the memory allocators, the bitwise cut-vertex lookup, and the `Solver` class declaration.
4. **`native/src/board.cpp`**: It holds the procedural grid builder, the reverse BFS pull-distance computation, the tunnel macro-move detection, and the path reconstructor.
5. **`native/src/heuristic.cpp`**: It holds the Hungarian minimum-cost bipartite matching and the greedy matching fallback. It also holds the LIS linear conflicts and the incremental 2-opt heuristic updates.
6. **`native/src/deadlock.cpp`**: It holds the 2x2 corner deadlock detection and the freeze analysis (`FrzFrozen`). It also holds the multi-corral scan (`FindPiCorral`) and the empty-goal access check (`HasDeadEmptyGoal`). The bipartite feasibility check uses Kuhn's augmenting paths.
7. **`native/src/solver.cpp`**: It holds the state allocation pool and the 4-ary min-heap priority queue. It also holds the 32-bit packed transposition table (`HashInsert`) and the partial-flood player reachability. The node expansion pipeline and the multi-threaded worker dispatch live here too.
8. **`native/src/tools/bench.cpp`**: It holds the command-line benchmark runner with per-thread win counts, spinner-safe output, and CSV reporting.
9. **`native/Makefile`**: It holds the multi-platform compiler rules. The rules compile each translation unit with link-time optimization (`-flto`).
